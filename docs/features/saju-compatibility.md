# Feature: 사주 궁합 (무료)

> 기준 문서는 [prd.md 8.4](../../prd.md#84-사주-궁합) 다. 여기는 구현 쪽 정본이다.

## User Goal

자녀가 상대 부모님 프로필을 볼 때, 우리 부모님과 **사주가 어떻게 맞는지**를 함께 보고
관심을 보낼지 정한다. 궁합이 좋은 분부터 먼저 볼 수도 있다.

## Summary

양쪽 부모님의 생년월일·양음력·출생시각으로 **사주팔자 네 기둥**을 세워 궁합 점수(30~99)와
근거를 낸다. 전면 무료이고(TODO-10) 유료 전환·부분 공개 장치를 두지 않는다.
외부 유료 API 를 쓰지 않고 **서버에서 직접 계산한다** — 절기와 60갑자는 천문 계산이라
매번 같은 답이 나오고, 사람의 생년월일을 외부로 내보낼 이유도 없다.

**모든 프로필에 사주가 있다.** 생년월일은 필수 항목이고(PRD 5.1), 팔자를 세우는 데 더
필요한 것은 양·음력과 출생시각뿐인데 둘 다 기본값이 있다 — 양력, 시각 모름(세 기둥).
그래서 `saju_infos` 는 **없어도 되는 보정값**이지 사주의 유무를 가르는 스위치가 아니다.
`SajuService.pillarsFor` 가 행이 없으면 `parent_profiles.birth_date` 로 폴백한다.

## 어디에 보이는가

| 자리 | 보여주는 것 | 코드 |
|---|---|---|
| 추천 카드 (뒤집은 뒤) | `별명 · 나이` / `을사일주` / `궁합 82점` | `GemCard` → `CompatibilityBadge` |
| 펼친 카드 | `을사일주 · 궁합 82점` | `ExpandedGemCard` |
| 받은 관심 카드 | 같은 표기 | 같은 컴포넌트 |
| 상세 프로필 | 별명·지역 바로 아래 `을사일주 · 궁합 82점` 한 줄 | `app/profile/[id].tsx` |
| 매칭(인연) 목록 | 지역 줄 아래 같은 한 줄 | `ParentProfileCard` |
| 매칭 성공 화면 | 같은 카드 | `app/matched/[id].tsx` |
| 대화방 헤더 | 상대 이름 아래 같은 한 줄 | `connections/[id]/index.tsx` |
| **부모님 웹** — 받으신 프로필 목록·상세 | 같은 글자 (`병인일주 · 궁합 74점`) | `parent-view.controller.ts` |
| 추천 순서 | 조건에 맞는 분들을 궁합 높은 순으로 (화면에 조작 장치 없음) | `DiscoveryService.recommend` |
| 부모님 프로필 작성 | 생년월일 아래 양력/음력 · 태어난 시간 | `(parent-setup)/profile-edit` |

**상대가 보이는 모든 화면이 같은 글자를 쓴다.** 자녀가 추천에서 보고, 관심을 보내고,
대화하고, 부모님께 보내드리기까지 같은 사람을 계속 보는데 한 곳이라도 표기가 다르면
다른 사람처럼 읽힌다. 부모님 화면의 궁합도 '부모님 본인과 상대'의 값이라 자녀가 보는
숫자와 같다.

> 한때 인연·부모님 화면에서는 뺐었다 — "궁합은 관심을 보낼지 정할 때 쓰는 정보이고
> 이미 이어진 뒤에는 판단을 바꾸지 않는다"고 봤다. 틀린 판단이었다. 부모님께
> 소개하고 만남을 잡는 내내 같은 카드를 보는데, 거기서만 사주가 사라지면
> 기능이 반쯤 빠진 것처럼 보인다. (`toItems` 에 `viewerProfileId` 를 넘기느냐가 그 경계다.)

> 부모님 화면은 서버 렌더 HTML 이라 한글 표(천간·지지)가 `parent-view.controller.ts`
> 에도 한 벌 있다. 모바일 `shared/config/saju.ts` 와 **글자가 같아야 한다.**

## 계산 — `apps/server/src/saju/lib/`

| 파일 | 역할 |
|---|---|
| `ganji.ts` | 천간·지지·오행 상수와 합·충·삼합·방합·원진 판정 |
| `solar-terms.ts` | 태양 겉보기황경 → 절기 시각, 율리우스일수 |
| `pillars.ts` | 사주팔자 네 기둥 |
| `compatibility.ts` | 궁합 점수·등급·근거 |

### 기둥 세우기

- **연주** — 입춘(황경 315°) 전이면 아직 지난 해다. 1월 1일생은 대부분 전년도 간지가 된다.
- **월주** — 12절(입춘부터 30° 간격)로 끊는다. 음력 초하루가 아니다. 월간은 오호둔(五虎遁).
- **일주** — 율리우스일수로 끊는 연속 60갑자. `korean-lunar-calendar` 의 일 간지와 대조해 맞췄다.
- **시주** — 23시부터 두 시간씩. 시간은 오서둔(五鼠遁). **23시 이후는 다음 날 자시**로 넘긴다(야자시).
- **음력 입력** — `korean-lunar-calendar`(한국천문연구원 기준, 1391~2050)로 양력으로 옮긴다.
  중국 농력이 아니라 KASI 음력을 쓰는 이유는 사용자가 대조할 만세력이 그쪽이기 때문이다.
- **표준시 보정** — 1954-03-21 ~ 1961-08-09 한국은 UTC+8:30 을 썼다. 이 시기에 적어 둔
  시계 시각을 KST 로 그냥 읽으면 30분이 밀려 시주가 통째로 어긋난다. 지금 만 65~72세인
  분들이 이 구간에 태어났다. (1908-04-01 ~ 1911-12-31 도 같다.)
- **경도 보정은 하지 않는다** — 서울 기준 −32분을 적용하는 유파가 있지만 한국천문연구원
  만세력은 표준시를 그대로 쓴다. 유파에 따라 갈리는 값을 서버가 임의로 고를 이유가 없다.

### 알려진 한계

절기 시각은 Meeus 저정밀 태양 위치식으로 구한다 — 황경 오차 약 0.01°, **시각으로 약 15분**.
절입과 15분 안쪽으로 태어난 경우 인쇄된 만세력과 월주가 갈릴 수 있다(확률 0.1% 미만).
정밀도를 더 올리려면 VSOP87 급수를 들여와야 하는데, 재미로 보는 참고 기능에 비해 표가 너무 크다.
**출생시각을 '모름'으로 두는 분이 더 많다는 점이 이 선택의 근거다.**

### 점수

기본 20점에 아래 항목을 더하고, 항목의 만점·최저점 합으로 **30~99** 에 정규화한다.

| 항목 | 배점 |
|---|---|
| 일간 (부부의 중심 자리) | 천간합 25 / 상생 18 / 비화 12 / 상극 7 / 충 4 |
| 일지 (배우자궁) | 육합 22 / 삼합 20 / 방합 14 / 동일 10 / 무관 6 / 충 −8 |
| 연지 (띠) | 삼합·육합 12 / 무관 5 / 충 −6 / 원진 −8 |
| 월지 (생활 리듬) | 합 8 / 무관 3 / 충 −5 |
| 오행 균형 (두 사람 합산 분포의 고름) | 0~18 |
| 음양 조화 (두 사람 합산) | 0~8 |
| 시지 (양쪽 다 시각을 알 때만) | 합 6 / 무관 2 / 충 −4 |

정규화 덕분에 **시주가 빠져도 점수가 깎이지 않는다** — 만점과 최저점이 함께 줄어든다.
대신 `confidence: 'medium'` 을 함께 내려보내고 화면이 "시주를 빼고 봤습니다"라고 밝힌다.

실측 분포(만 50세 이상 표본 2,016쌍): 최소 43 / 1사분위 64 / 중앙 69 / 3사분위 74 / 최대 92, 평균 69.0.
`distribution.spec.ts` 가 이 성질(뭉치지 않을 것, 40점 미만 5% 이하, 90점 이상 10% 이하)을 지킨다.

### 화면에는 두 값만 — 일주와 점수

만들면서 세 번 덜어냈고, 남은 것은 `을사일주` 와 `궁합 82점` 뿐이다.

| 뺀 것 | 이유 |
|---|---|
| 등급 문구 (`천생연분`·`무난한 궁합`) | 숫자는 참고로 읽히지만 **문장은 결론으로 읽힌다.** 서비스가 두 사람 사이를 판정하는 모양이 되고, 점수가 낮게 나온 상대도 누군가의 부모님이다 |
| 근거 풀이 (`· 배우자 자리가 육합입니다 …`) | 이 화면에서 정하는 건 "관심을 보낼까" 하나다. 설명이 길어질수록 그 판단 대신 해석을 읽게 된다 |
| 두 사람의 네 기둥 | 아무도 안 그리는데 생년월일이 특정되는 값이었다 |
| `재미로 보는 참고 정보입니다` | 위를 다 덜어내니 단정할 문장 자체가 남지 않았다 |

`SajuCompatibility.reasons` / `confidence` 는 **엔진에 그대로 남아 있다** (테스트가
이 값들로 규칙을 검증한다). 다만 지금은 어느 화면도 그리지 않는다.

## 문구는 전부 모바일에 있다

서버는 **코드만** 내려보낸다: 점수, `SajuGrade`, `SajuReasonCode[]`, 천간·지지 **인덱스**.
한글은 `apps/mobile/src/shared/config/saju.ts` 한 곳에서 붙는다.
서버가 '갑자'라는 글자를 만들기 시작하면 같은 표가 양쪽에 생기고 언젠가 어긋난다.

## 프라이버시

- **`saju_infos.is_public` 은 생년월일·출생시각 자체의 노출만 가른다.** 궁합 계산은 이 값과
  무관하게 돈다 — 사주 칸을 둔 이유가 궁합이고(PRD 5.3), 점수와 근거 코드로는 생년월일이
  복원되지 않는다.
**상대에게 나가는 사주 값은 두 개뿐이다** — 일주와 궁합 점수.

- **원본 생년월일·출생시각은 어느 응답에도 없다.** `PublicProfileDto.saju` 를 없앴고,
  상세의 '사주 정보' 섹션도 지웠다. 정확한 생년월일은 PRD 7 이 비공개로 못박은 값이라
  사주 때문에 그 원칙이 뚫리면 안 된다. 본인 프로필 조회(`/parent-profile`)에는 그대로 온다.
- **네 기둥도 없다.** 기둥 넷이면 60갑자 안에서 생년월일이 거의 특정된다.
- **일주 하나(`DiscoveryItemDto.dayPillar`)는 나간다.** 60일 주기라 나이를 알아도 후보
  날짜가 여럿 남는다 — 네 기둥이 날짜를 하나로 좁히는 것과 성격이 다르다.
- `saju_infos.is_public` 은 **항상 false** 로 쓴다 (위 '입력 화면' 참조). 우리 API 가
  원본을 안 내보내도 RLS 정책이 열려 있으면 PostgREST 로 직접 읽히기 때문이다.

## 추천 순서 — 조건이 아니라 순서다

**필터에 궁합 항목이 없다.** 정렬 선택지도 최소 점수도 두지 않는다. 처음엔 둘 다 넣었다가
걷어냈고, 이유는 두 가지다:

- "궁합 낮은 순으로 보고 싶다"는 뜻이 없다. 뜻이 하나뿐인 선택지는 선택지가 아니다.
- 최소 점수를 두면 **사주를 적지 않은 분이 통째로 빠진다.** 사주는 선택 입력인데
  (PRD 5.3), 점수로 거르는 순간 선택 항목이 사실상의 자격 요건이 된다.

그래서 사용자가 정하는 것은 조건(거리·나이·목적…)까지고, 그 안에서 누구를 먼저
보여줄지는 서비스가 정한다.

동작 (`DiscoveryService.recommend`):

- 궁합은 DB 가 모르는 값이라 SQL 로 정렬할 수 없다. 후보 **최대 200명**
  (`COMPATIBILITY_POOL`, 최근 활동 순)을 받아 서버가 매기고 자른다.
  홈이 하루 여섯 장이라 이 깊이면 충분하다.
- 커서는 타임스탬프가 아니라 정렬된 목록의 **위치**(`o:20`)다.
- 동점이면 pool 순서(최근 활동 순)가 남는다 — `Array.sort` 는 안정 정렬이다.
- 팔자를 못 세우는 예외(날짜 손상·변환표 밖)는 점수 `-1` 로 **뒤로 밀릴 뿐 빠지지 않고**,
  내 쪽이 그러면 최근 활동 순 경로로 돌아간다(커서도 타임스탬프). 추천 수는 평소와 같다.

## 데이터

**새 컬럼이 없다.** 기존 `saju_infos` 를 그대로 읽고, 사주팔자는 저장하지 않고 매번 계산한다.

`discovery_filters` 에 `sort` / `min_compatibility` 를 넣었다가
(`20260909120000_discovery_saju_sort.sql`) 위 이유로 곧바로 되돌렸다
(`20260909170000_drop_discovery_saju_sort.sql`). 적용된 마이그레이션은 고쳐 쓰지 않는다.

## 입력 화면 — 생년월일 바로 아래

**'사주 정보' 섹션이 따로 없다.** 기본정보의 생년월일 칸 밑에 이어서 받는다:

```
생년월일  [필수]
연도-월-일 순으로 적어주세요 (예: 1958-04-11) · 만 50세 이상만 등록하실 수 있습니다
[ 1969-01-11 ]
┌────────────────────────────────────────────────┐
│ 이 날짜로 사주를 세웁니다. 사주를 기반으로 프로필을  │
│ 추천해드리고 상대 부모님과의 궁합 점수를 보여드립니다. │
└────────────────────────────────────────────────┘

양력 · 음력  [필수]      ( 양력 ) ( 음력 )
태어난 시간              [ 07:30 ]  ( 모름 )
```

- **날짜를 적는 자리에서 용도를 알린다.** 아래 양·음력 칸까지 내려가서야 눈치채면 이미
  대충 적은 뒤다. 이 날짜는 나이 계산에만 쓰이는 게 아니다.
- **날짜를 다시 묻지 않는다.** 사주용 날짜 칸을 따로 두면 두 값이 언젠가 어긋나고, 어느
  쪽으로 사주를 세웠는지 아무도 설명하지 못한다.
- **'입력 안 함'이 없다.** 생년월일이 필수라 사주는 어차피 세워진다. 끄는 선택지를 두면
  "사주를 안 쓴 사람"이라는 상태가 생기고 카드가 두 종류로 갈린다.
- **공개 여부도 묻지 않는다.** 상대에게 나가는 사주 값은 일주와 궁합 점수뿐이고 원본
  생년월일·출생시각은 누구에게도 안 나간다(PRD 7) — 켜고 끌 것이 남지 않았다.
  `saju_infos.is_public` 은 **항상 false 로 쓴다**: 이 컬럼이 실제로 여는 문은 RLS 정책
  `saju_public_read` 이고, true 면 인증된 아무나 PostgREST 로 그 행(정확한 생년월일)을
  직접 읽을 수 있다.
- 태어난 시간은 숫자만 눌러도 된다 (`0730` → `07:30`). 콜론을 직접 치게 하면 숫자 키패드에서
  자판을 바꿔야 해서 이 나이대의 자녀분들이 가장 자주 멈추는 자리가 된다.
- 사주는 프로필을 저장할 때마다 함께 보낸다. 사주 칸을 건드렸을 때만 보내면 생년월일만
  고친 뒤에 사주가 옛 날짜로 남아 궁합이 엉뚱하게 나온다.
